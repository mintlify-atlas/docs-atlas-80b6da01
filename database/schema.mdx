<Note>
  Kairo requires **PostgreSQL 14 or later**. The database is hosted on [Supabase](https://supabase.com), which provides managed PostgreSQL with built-in auth, Row Level Security, and real-time capabilities.
</Note>

The schema defines **14 tables** organized into five functional groups. All tables have Row Level Security enabled — see [RLS policies](/database/rls-policies) for access rules.

## Table overview

| Table | Group | Purpose |
|---|---|---|
| `users` | Users | All platform users — coders and Team Leaders |
| `soft_skills_assessment` | Users | Initial soft-skills evaluation per coder |
| `modules` | Academic content | Bootcamp modules (e.g. Python, JavaScript) |
| `topics` | Academic content | Specific topics within each module |
| `moodle_progress` | Academic content | Academic progress synced from Moodle |
| `coder_struggling_topics` | Academic content | N:M relation tracking difficulty topics |
| `complementary_plans` | Learning plans | AI-generated personalized learning plans (the 6 Cards) |
| `plan_activities` | Learning plans | Daily activities inside each plan |
| `activity_progress` | Learning plans | Tracks which activities each coder has completed |
| `evidence_submissions` | Learning plans | Files and links uploaded as evidence |
| `tl_feedback` | Communication | TL messages and feedback to coders |
| `risk_flags` | Analytics | At-risk alerts generated automatically or manually |
| `ai_reports` | Analytics | Executive reports generated by AI for TLs |
| `ai_generation_log` | Analytics | Audit log of all AI calls |

<Accordion title="users — Coders and Team Leaders">

Stores every user of the platform. The `role` column determines whether a user is a coder or a Team Leader, which drives all RLS policies.

```sql
CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  email VARCHAR(100) UNIQUE NOT NULL,
  password VARCHAR(255) NOT NULL,
  full_name VARCHAR(150) NOT NULL,
  role role_enum NOT NULL,
  clan_id VARCHAR(50),
  first_login BOOLEAN DEFAULT TRUE,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | `SERIAL` | `PRIMARY KEY` | Auto-incrementing user ID |
| `email` | `VARCHAR(100)` | `UNIQUE NOT NULL` | Login email address |
| `password` | `VARCHAR(255)` | `NOT NULL` | Hashed password |
| `full_name` | `VARCHAR(150)` | `NOT NULL` | Display name |
| `role` | `role_enum` | `NOT NULL` | Either `'coder'` or `'tl'` |
| `clan_id` | `VARCHAR(50)` | — | Clan name: `Turing`, `Tesla`, or `McCarthy` |
| `first_login` | `BOOLEAN` | `DEFAULT TRUE` | Drives the onboarding flow; set to `false` after first login |
| `created_at` | `TIMESTAMP` | `DEFAULT CURRENT_TIMESTAMP` | Account creation time |

**Indexes:** `idx_users_email`, `idx_users_role`, `idx_users_clan_id`

</Accordion>

<Accordion title="soft_skills_assessment — Initial skill assessment">

Stores the result of the onboarding soft-skills evaluation. Each coder has exactly one assessment (`UNIQUE` on `coder_id`). Skills are scored 1–5.

```sql
CREATE TABLE soft_skills_assessment (
  id SERIAL PRIMARY KEY,
  coder_id INT NOT NULL UNIQUE,
  autonomy INT NOT NULL CHECK (autonomy BETWEEN 1 AND 5),
  time_management INT NOT NULL CHECK (time_management BETWEEN 1 AND 5),
  problem_solving INT NOT NULL CHECK (problem_solving BETWEEN 1 AND 5),
  communication INT NOT NULL CHECK (communication BETWEEN 1 AND 5),
  teamwork INT NOT NULL CHECK (teamwork BETWEEN 1 AND 5),
  learning_style learning_style_enum NOT NULL,
  raw_answers JSONB,
  assessed_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (coder_id) REFERENCES users(id) ON DELETE CASCADE
);
```

| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | `SERIAL` | `PRIMARY KEY` | — |
| `coder_id` | `INT` | `UNIQUE NOT NULL`, FK → `users.id` | One assessment per coder |
| `autonomy` | `INT` | `CHECK (1–5)` | Autonomy score |
| `time_management` | `INT` | `CHECK (1–5)` | Time management score |
| `problem_solving` | `INT` | `CHECK (1–5)` | Problem-solving score |
| `communication` | `INT` | `CHECK (1–5)` | Communication score |
| `teamwork` | `INT` | `CHECK (1–5)` | Teamwork score |
| `learning_style` | `learning_style_enum` | `NOT NULL` | Preferred learning modality |
| `raw_answers` | `JSONB` | — | Full onboarding answers array `[{questionId, optionId, score}]` for audit and re-processing |
| `assessed_at` | `TIMESTAMP` | `DEFAULT CURRENT_TIMESTAMP` | Assessment timestamp |

**Indexes:** `idx_soft_skills_coder`

<Note>
  The `raw_answers` column was added in [migration 002](/database/migrations). If you are working with an older schema version, apply that migration before inserting assessments.
</Note>

</Accordion>

<Accordion title="moodle_progress — Academic progress sync">

Tracks each coder's progress within a module, synced from the Moodle LMS. The `(coder_id, module_id)` pair is unique, so a coder has one progress record per module.

```sql
CREATE TABLE moodle_progress (
  id SERIAL PRIMARY KEY,
  coder_id INT NOT NULL,
  module_id INT NOT NULL,
  current_week INT NOT NULL,
  weeks_completed JSONB DEFAULT '[]'::jsonb,
  struggling_topics TEXT[] DEFAULT '{}',
  average_score DECIMAL(5,2) DEFAULT 0,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  UNIQUE (coder_id, module_id),
  FOREIGN KEY (coder_id) REFERENCES users(id) ON DELETE CASCADE,
  FOREIGN KEY (module_id) REFERENCES modules(id) ON DELETE CASCADE
);
```

| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | `SERIAL` | `PRIMARY KEY` | — |
| `coder_id` | `INT` | `NOT NULL`, FK → `users.id` | The coder |
| `module_id` | `INT` | `NOT NULL`, FK → `modules.id` | The module |
| `current_week` | `INT` | `NOT NULL` | Week the coder is currently on |
| `weeks_completed` | `JSONB` | `DEFAULT '[]'` | Array of completed week numbers, e.g. `[1, 2, 3]` |
| `struggling_topics` | `TEXT[]` | `DEFAULT '{}'` | Free-text array of topics the coder is struggling with |
| `average_score` | `DECIMAL(5,2)` | `DEFAULT 0` | Overall module score (0–100) |
| `updated_at` | `TIMESTAMP` | `DEFAULT CURRENT_TIMESTAMP` | Last sync timestamp |

**Indexes:** `idx_moodle_coder`, `idx_moodle_score`

</Accordion>

<Accordion title="topics — Module topics">

Granular topics within a module. Used to track which specific concepts a coder struggles with via `coder_struggling_topics`.

```sql
CREATE TABLE topics (
  id SERIAL PRIMARY KEY,
  module_id INT NOT NULL,
  name VARCHAR(200) NOT NULL,
  category VARCHAR(100),
  FOREIGN KEY (module_id) REFERENCES modules(id) ON DELETE CASCADE
);
```

| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | `SERIAL` | `PRIMARY KEY` | — |
| `module_id` | `INT` | `NOT NULL`, FK → `modules.id` | Parent module |
| `name` | `VARCHAR(200)` | `NOT NULL` | Topic name (e.g. `'Async/Await'`) |
| `category` | `VARCHAR(100)` | — | Grouping label (e.g. `'Conceptos'`, `'Avanzado'`) |

**Indexes:** `idx_topics_module`, `idx_topics_category`

</Accordion>

<Accordion title="coder_struggling_topics — Difficulty tracking (N:M)">

Many-to-many join table between coders and the topics they are struggling with. A unique constraint prevents duplicate entries.

```sql
CREATE TABLE coder_struggling_topics (
  id SERIAL PRIMARY KEY,
  coder_id INT NOT NULL,
  topic_id INT NOT NULL,
  reported_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  UNIQUE (coder_id, topic_id),
  FOREIGN KEY (coder_id) REFERENCES users(id) ON DELETE CASCADE,
  FOREIGN KEY (topic_id) REFERENCES topics(id) ON DELETE CASCADE
);
```

| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | `SERIAL` | `PRIMARY KEY` | — |
| `coder_id` | `INT` | `NOT NULL`, FK → `users.id` | The coder |
| `topic_id` | `INT` | `NOT NULL`, FK → `topics.id` | The struggled topic |
| `reported_at` | `TIMESTAMP` | `DEFAULT CURRENT_TIMESTAMP` | When the difficulty was reported |

**Indexes:** `idx_struggling_coder`

</Accordion>

<Accordion title="complementary_plans — AI-generated learning plans (the 6 Cards)">

Holds the AI-generated personalized learning plans. Each coder gets up to 6 active plans at a time — 2 high priority, 2 medium, and 2 low — which appear as cards in the dashboard.

```sql
CREATE TABLE complementary_plans (
  id SERIAL PRIMARY KEY,
  coder_id INT NOT NULL,
  module_id INT NOT NULL,
  plan_content JSONB NOT NULL,
  priority_level priority_level_enum DEFAULT 'medium',
  soft_skills_snapshot JSONB,
  moodle_status_snapshot JSONB,
  is_active BOOLEAN DEFAULT TRUE,
  generated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (coder_id) REFERENCES users(id) ON DELETE CASCADE,
  FOREIGN KEY (module_id) REFERENCES modules(id) ON DELETE CASCADE
);
```

| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | `SERIAL` | `PRIMARY KEY` | — |
| `coder_id` | `INT` | `NOT NULL`, FK → `users.id` | Plan owner |
| `module_id` | `INT` | `NOT NULL`, FK → `modules.id` | Related module |
| `plan_content` | `JSONB` | `NOT NULL` | Full structured plan generated by AI |
| `priority_level` | `priority_level_enum` | `DEFAULT 'medium'` | Card priority: `low`, `medium`, or `high` |
| `soft_skills_snapshot` | `JSONB` | — | Soft-skills values at generation time (for audit) |
| `moodle_status_snapshot` | `JSONB` | — | Moodle progress at generation time (for audit) |
| `is_active` | `BOOLEAN` | `DEFAULT TRUE` | Only active plans appear on the coder dashboard |
| `generated_at` | `TIMESTAMP` | `DEFAULT CURRENT_TIMESTAMP` | Generation timestamp |

**Indexes:** `idx_plans_coder`, `idx_plans_active`, `idx_plans_priority`

<Tip>
  To fetch a coder's 6 cards in display order, query: `SELECT * FROM complementary_plans WHERE coder_id = $1 AND is_active = true ORDER BY priority_level DESC`
</Tip>

</Accordion>

<Accordion title="plan_activities — Daily activities within a plan">

```sql
  activity_type activity_type_enum,
  skill_focus VARCHAR(100),

```

| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | `SERIAL` | `PRIMARY KEY` | — |
| `plan_id` | `INT` | `NOT NULL`, FK → `complementary_plans.id` | Parent plan |
| `day_number` | `INT` | `NOT NULL` | Day within the plan schedule |
| `title` | `VARCHAR(200)` | `NOT NULL` | Activity title |
| `description` | `TEXT` | — | Detailed instructions |

| `activity_type` | `activity_type_enum` | — | `guided`, `semi_guided`, or `autonomous` |

</Accordion>

<Accordion title="activity_progress — Activity completion tracking">

Tracks whether a coder has completed each activity. The unique constraint on `(activity_id, coder_id)` ensures one progress record per coder per activity.

```sql
CREATE TABLE activity_progress (
  id SERIAL PRIMARY KEY,
  activity_id INT NOT NULL,
  coder_id INT NOT NULL,
  completed BOOLEAN DEFAULT FALSE,
  reflection_text TEXT,
  time_spent_minutes INT,
  completed_at TIMESTAMP NULL,
  UNIQUE (activity_id, coder_id),
  FOREIGN KEY (activity_id) REFERENCES plan_activities(id) ON DELETE CASCADE,
  FOREIGN KEY (coder_id) REFERENCES users(id) ON DELETE CASCADE
);
```

| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | `SERIAL` | `PRIMARY KEY` | — |
| `activity_id` | `INT` | `NOT NULL`, FK → `plan_activities.id` | The activity |
| `coder_id` | `INT` | `NOT NULL`, FK → `users.id` | The coder |
| `completed` | `BOOLEAN` | `DEFAULT FALSE` | Completion flag |
| `reflection_text` | `TEXT` | — | Coder's written reflection after completing |
| `time_spent_minutes` | `INT` | — | Actual time spent |
| `completed_at` | `TIMESTAMP` | `NULL` | Completion timestamp; `NULL` when not yet done |

**Indexes:** `idx_progress_activity`, `idx_progress_coder`, `idx_progress_completed`

</Accordion>

<Accordion title="tl_feedback — TL messages to coders">

Holds all feedback and messages sent by Team Leaders to coders. The `is_read` flag drives the notification bell UI — an unread message shows a red dot.

```sql
CREATE TABLE tl_feedback (
  id SERIAL PRIMARY KEY,
  coder_id INT NOT NULL,
  tl_id INT NOT NULL,
  plan_id INT,
  feedback_text TEXT NOT NULL,
  feedback_type feedback_type_enum,
  is_read BOOLEAN DEFAULT FALSE,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (coder_id) REFERENCES users(id) ON DELETE CASCADE,
  FOREIGN KEY (tl_id) REFERENCES users(id) ON DELETE CASCADE,
  FOREIGN KEY (plan_id) REFERENCES complementary_plans(id) ON DELETE SET NULL
);
```

| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | `SERIAL` | `PRIMARY KEY` | — |
| `coder_id` | `INT` | `NOT NULL`, FK → `users.id` | Feedback recipient |
| `tl_id` | `INT` | `NOT NULL`, FK → `users.id` | Feedback author (TL) |
| `plan_id` | `INT` | FK → `complementary_plans.id` `ON DELETE SET NULL` | Optional: the plan this feedback relates to |
| `feedback_text` | `TEXT` | `NOT NULL` | Message content |
| `feedback_type` | `feedback_type_enum` | — | `weekly`, `activity`, or `general` |
| `is_read` | `BOOLEAN` | `DEFAULT FALSE` | `false` = notification bell shows red dot |
| `created_at` | `TIMESTAMP` | `DEFAULT CURRENT_TIMESTAMP` | — |

**Indexes:** `idx_feedback_coder`, `idx_feedback_tl`, `idx_feedback_is_read`, `idx_feedback_coder_unread`

</Accordion>

<Accordion title="risk_flags — At-risk alerts">

Records alerts for coders who have been identified as at-risk, either by the automated risk detector or manually by a TL.

```sql
CREATE TABLE risk_flags (
  id SERIAL PRIMARY KEY,
  coder_id INT NOT NULL,
  risk_level risk_level_enum NOT NULL,
  reason TEXT NOT NULL,
  auto_detected BOOLEAN DEFAULT TRUE,
  detected_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  resolved BOOLEAN DEFAULT FALSE,
  resolved_at TIMESTAMP NULL,
  FOREIGN KEY (coder_id) REFERENCES users(id) ON DELETE CASCADE
);
```

| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | `SERIAL` | `PRIMARY KEY` | — |
| `coder_id` | `INT` | `NOT NULL`, FK → `users.id` | At-risk coder |
| `risk_level` | `risk_level_enum` | `NOT NULL` | `low`, `medium`, or `high` |
| `reason` | `TEXT` | `NOT NULL` | Human-readable explanation of the risk |
| `auto_detected` | `BOOLEAN` | `DEFAULT TRUE` | `true` = flagged by AI; `false` = flagged manually by TL |
| `detected_at` | `TIMESTAMP` | `DEFAULT CURRENT_TIMESTAMP` | Detection time |
| `resolved` | `BOOLEAN` | `DEFAULT FALSE` | Whether the TL has resolved the alert |
| `resolved_at` | `TIMESTAMP` | `NULL` | Resolution timestamp |

**Indexes:** `idx_risk_coder`, `idx_risk_level`, `idx_risk_resolved`

</Accordion>

<Accordion title="ai_generation_log — AI audit log">

An immutable audit trail for every call made to an AI agent. Used to debug outputs, measure performance, and track costs.

```sql
CREATE TABLE ai_generation_log (
  id SERIAL PRIMARY KEY,
  coder_id INT,
  agent_type ai_agent_enum NOT NULL,
  input_payload JSONB NOT NULL,
  output_payload JSONB NOT NULL,
  model_name VARCHAR(100),
  execution_time_ms INT,
  success BOOLEAN DEFAULT TRUE,
  error_message TEXT,
  generated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (coder_id) REFERENCES users(id) ON DELETE SET NULL
);
```

| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | `SERIAL` | `PRIMARY KEY` | — |
| `coder_id` | `INT` | FK → `users.id` `ON DELETE SET NULL` | Related coder (nullable; `NULL` for cohort-level calls) |
| `agent_type` | `ai_agent_enum` | `NOT NULL` | Which AI agent was invoked |
| `input_payload` | `JSONB` | `NOT NULL` | Full request sent to the AI model |
| `output_payload` | `JSONB` | `NOT NULL` | Full response received from the AI model |
| `model_name` | `VARCHAR(100)` | — | Model identifier (e.g. `gpt-4o`) |
| `execution_time_ms` | `INT` | — | Round-trip latency in milliseconds |
| `success` | `BOOLEAN` | `DEFAULT TRUE` | `false` if the call errored |
| `error_message` | `TEXT` | — | Error detail when `success = false` |
| `generated_at` | `TIMESTAMP` | `DEFAULT CURRENT_TIMESTAMP` | Call timestamp |

**Indexes:** `idx_log_agent`, `idx_log_coder`, `idx_log_date`

</Accordion>
